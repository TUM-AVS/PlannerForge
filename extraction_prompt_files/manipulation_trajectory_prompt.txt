[TASK]
You will be given a SUMO `.vehicles.rou.xml` route file and a user request to redirect one or more vehicles to a new target edge. Emit the **complete updated route file** with the requested change applied. Return only the XML — no commentary, no markdown fences.

The user identifies vehicles by their numeric `id` attribute and target edges by edge id. The downstream simulator requires the new route to consist of an ordered sequence of edges connected via the network's `<connection>` elements (see the network summary from the previous step). You may insert intermediate edges to bridge non-adjacent endpoints.

[CP]
Rules when editing a vehicle's route:

- DO NOT change the vehicle's `id`, `depart`, `departLane`, `departPos`, `departSpeed`, or `type`. The user is only redirecting the vehicle's destination, not respawning it.
- DO NOT change the FIRST edge in the route — that edge corresponds to the vehicle's starting position and must stay in sync with `departPos`.
- DO append the target edge as the LAST edge. Insert any intermediate edges required to walk a valid path from the current last edge to the target edge, using the network's `<connection>` adjacency. Transitive connections are allowed (X→Y, Y→Z lets you write `X Y Z`).
- DO NOT modify other vehicles. Their `<vehicle>` and `<route>` elements must remain byte-equivalent.
- DO NOT keep `arrivalPos`, `arrivalLane`, or `insertionChecks="none"` attributes on a vehicle whose route you change. Those were tied to the OLD destination — remove them. (`insertionChecks="none"` disables safety checks and is only safe for exact trajectory replay, not for a re-routed vehicle.)
- Honour vClass: if the network summary says edge E `disallow`s the vehicle's vClass, do NOT route through E. Pick an alternative path. If no valid path exists, emit the route file unchanged and add a comment line `<!-- vehicle <id> cannot reach <target> within vClass constraints -->`.
- Return the COMPLETE updated file. Do not abbreviate, do not use `...`, do not omit any vehicle.

  1. (Locate the target vehicle) Find each `<vehicle id="...">` element matching the user-named vid(s).

  3. (Pick the target edge) From the user request, identify the destination edge id.
  4. (Walk the path) Using the network summary from the previous step, find a sequence of edges from the current last edge to the target edge that respects `<connection>` adjacency and the vehicle's vClass. Allow transitive multi-hop paths.

  6. (Leave other vehicles alone) Every untouched `<vehicle>` and `<vType>` element must appear byte-equivalent in your output.
  7. (Emit) Return the COMPLETE updated route file.

End each step on its own line (e.g. `Step 1 (locate): found vid=20054`, `Step 4 (walk): 544 → 211 direct`), then emit the final XML as the last block of output.
